SECTION 02 / CASE STUDY

TIKARIY

THE CHALLENGE

An educational toy brand was selling through WhatsApp messages and a spreadsheet. Orders were lost, stock was guesswork, and every invoice was written by hand.

The platform had to replace that process without losing the conversational sales channel the business depended on. That meant a real catalog, real payments, automatic invoicing, and an admin surface non-technical staff could operate on the first day — all delivered by one developer on a fixed timeline.

ENGINEERING DECISIONS
EXPAND TO READ THE REASONING

The storefront, the cart and the admin dashboard need overlapping but different slices of the same data. With REST that meant either three sets of endpoints or over-fetching everywhere. A single typed schema let each surface ask for exactly what it renders, and code generation turned that schema into TypeScript types on both sides — so a field rename breaks the build instead of the checkout.

TRADE-OFFCaching is harder than with plain HTTP endpoints. Persisted queries and per-resolver caching handled the hot paths; the rest was measured before it was optimized.

Commerce is a relational problem. Orders reference products, prices reference currencies, invoices reference orders, and none of those relationships may drift. Postgres gives transactions, foreign keys and check constraints, so the invariants that matter to the business are enforced by the database rather than by hope and application code.

DETAILMoney is stored as integer minor units. Product attributes that vary by category live in JSONB, which keeps the core tables narrow without giving up query power.

Version one was a single Next.js app talking straight to the database. It shipped fast and taught me where the real complexity was: pricing, stock and invoicing. Those rules kept leaking into route handlers, so the domain moved into a NestJS service with its own modules, and the frontend became a client of a contract instead of an owner of business logic.

RESULTThe admin dashboard was added later against the same API, with no changes to the storefront. That is the test I use for whether a boundary was drawn in the right place.

SECTION 07

BEHIND THE CODE

Engineering notes — the reasoning behind decisions, written while the work was still fresh.

Three clients, one dataset. The storefront wants images and prices, the cart wants stock and totals, the admin wants everything plus audit fields. REST would have meant a set of endpoints per client, or one fat endpoint that nobody could change safely.

The schema became the shared vocabulary of the project. Once it existed, generated types made the client and the server agree by construction, and adding the admin dashboard cost days rather than weeks. The price is caching discipline and resolver hygiene, which is a price worth paying when the data graph is genuinely a graph.

One module per domain concept, not per technical layer. Catalog, orders, billing and auth each own their entities, services and resolvers, and expose a small surface to the rest of the app. Controllers and resolvers stay thin: they validate input and delegate.

The rule I hold to is that a module may depend on an interface but never on another module's internals. It makes the boring changes boring, and it makes the interesting ones — a new payment provider, a second storefront — local instead of structural.

Start from the invariants. Which two rows must never contradict each other? Those relationships become foreign keys and check constraints before any code is written, because the database is the last place a bug can be caught cheaply.

After that it is measurement: read the query plans, index the paths the product actually walks, and keep hot tables narrow. Flexible attributes go in JSONB, money in integers, timestamps in UTC. Most scaling problems I have met were schema problems wearing a performance costume.

The checkout is the easy part. The hard parts are the states around it: a payment that succeeded while the browser closed, stock reserved for a cart nobody returns to, an invoice that must exist exactly once. Commerce is a study in idempotency.

The other lesson was about people. The admin dashboard decided whether the platform was adopted at all, and no amount of backend elegance would have compensated for a confusing product form. Shipping software means shipping the part someone has to use every morning.
